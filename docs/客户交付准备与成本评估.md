## 二、给客户前必须补齐的 9 项

### 1. 环境与安装（阻断级）
- Python 3.11 + `playwright` + `msedge` + `rapidocr_onnxruntime`（后者纯 CPU、模型随 wheel，**零下载**）
- **`TMP`/`TEMP` 必须重定向到可写目录**：否则 `mkdtemp EPERM` 直接启动失败（2026-10-27 踩过）
- 沙箱/杀软放行浏览器驱动子进程（命名管道）
- 交付形式：一键安装脚本 + 自检命令（能列出 canvas、能读到 token 才算装好）

### 2. 登录态与账号（运营级）
- token 会过期，**无人值守无法自我恢复** → 需要：客户提供专用账号 + 定期人工登录，或做账号托管方案（涉及安全评审，不建议一上来就做）
- token **绝不落盘、绝不打印**（SOP §8）；日志只报长度/存在性
- 建议：客户侧给一个"标注专用账号"，与业务账号隔离

### 3. 每本新书的标定（工程级）
- 栏缝/阈值/行高大部分自适应（本次实测：p27 自动切出双栏 `[(66,590),(623,1145)]`）
- 但**每本书首 1 页必须抽样确认**：栏数、题号规则（`1.` vs `(1)`）、答案页位置（按章节标题找，不能按页码偏移算，SOP §5.4）
- 产出：`data/derived/measure/<page>.measure.json` + contact sheet，人眼 1 分钟确认

### 4. 业务口径配置化（产品级）
必须做成配置项，不能写死：
- 选项是否每项单独 W 框（R02）还是合并一个框
- 组合题的小题选项是否并入 Q（R03）
- 无解析时是否画空框（SOP：**不画**）
- Q 框范围：题干行 vs 含选项（当前测量输出的是题块，需按口径裁切）

### 5. 数据安全闸门（合规级）
SOP 里的三档必须原样保留，一条都不能省：
- 识别后核对 `results[].question_order` 全部等于预期题号，不等就重试一次，仍不等**中止不提交**
- 提交后核对 `inserted === true` 且 `question_order` 符合预期
- `ocr_delete_zones` 永远不含 `question`/`answer`
- 建议加：**dry-run 模式**（测量+画框+识别，但不提交），客户先跑一天看报告

### 6. 可观测与可审计（交付级）
- 每页留：measure.json（含低置信标记）、contact sheet、提交前后 counts、服务端回读 JSON
- 失败必须留证据（截图 + 状态栏 counts + 接口响应），不能只留一行报错
- 日报：成功题数 / 返工题数 / 中止原因分布

### 7. 失败恢复（运营级）
- 每题开始前的全量重置路径（SOP #24）保留为兜底
- 幂等：同一题重复跑不得产生重复框（先读 back，再决定画/删）
- 回滚：删题让后续题号前移且不可逆 → **动手前先导出该题 JSON**

### 8. 交付物清单
- 安装与自检脚本
- RUNBOOK（含本会话新增的坑：异步加载、起点落在旧框、节点徽标）
- SOP 增补页（原 SOP 的 ego 段落替换为 playwright 等价物）
- 验收用例 3 条：题目页测量 / 答案切分 / 单题端到端提交

### 9. 授权与法务
- 客户须书面确认：测试书 vs 正式书、可写入范围、返工责任
- 平台条款层面确认自动化标注是否被允许（这属于客户侧确认，不由我们推定）

## 三、成本模型（实测数据，非估算）

### 3.1 单页人工成本（SOP §10 实测）
| 环节 | 耗时 |
|---|---|
| 版面测量（墨迹投影 + 答案行切分） | ~15 分钟（一次性/页） |
| 单题录入（画框→题型→识别→提交） | 12–25 秒（中位 13 秒） |
| 单题全量重置（兜底路径） | ~40 秒 |
| **一页 14 题合计** | **~20 分钟** |

### 3.2 单页自动化成本（本会话实测口径）
| 环节 | 耗时 | 说明 |
|---|---|---|
| 源图下载 | <3 秒 | OSS 直链，无需鉴权 |
| 题目页测量（含 OCR 71 atom） | 30–60 秒 | CPU，无人值守 |
| 答案页切分（含 OCR） | 20–40 秒 | 同上 |
| 人眼确认 contact sheet | 1–2 分钟 | 低置信项才需要细看 |
| 录入（同平台行为） | ~5 分钟/14 题 | 与人工一致，瓶颈在 OCR 服务端 6–12 秒硬成本 |
| **一页合计** | **~8–10 分钟** | 相对人工 **降 50–60%** |

### 3.3 Token 成本（本轮最大收益）
| 方式 | 单页请求数 × 上下文 | 单页 tokens |
|---|---|---|
| 旧法（裁一块 → 看 → 再裁） | 67 × 96.9k | **6.5M** |
| contact sheet（一张图定稿） | 3–5 × ~25k | **~0.1M** |
| 降幅 | — | **约 65×** |

- 100 页：6.5M × 100 = **650M** → **~10M**
- 折算费用（按 $0.5/M 输入价）：**$325 → $5** 量级（价格随模型变，只作数量级参考）

### 3.4 结论
- **测量环节的成本已从"人工 15 分钟/页"变成"脚本 1 分钟 + 人眼 1 分钟"**，这是最大的单项改善
- 录入环节的 6–12 秒 OCR 往返是**服务端硬成本，不能省**（SOP 已论证：缓存/降频会丢当场核对能力）
- 目前每页 8–10 分钟的现实瓶颈是**画框与提交的可靠性**，不是测量

## 四、风险清单（交付前必须让客户知情）

1. **答案行内切分未达生产标准**：13/14 锚点 + 归属错行，必须配人眼确认；不确认就提交会污染数据
2. **画框起点冲突**：起手落在已有框的 resize handle 内会变成移动旧框（SOP #2/#26），软件层需做"起点避让"
3. **题目加载异步**：dblclick 后必须轮询 counts 非零再画，否则框被重渲染吞掉（本轮实测）
4. **答案区空白不等于故障**：未加载题目时答案画布本来就是空的
5. **题号错位**（SOP #21）：节点 label 与服务端 order 可能差一位甚至更多，删过题的目录尤其危险
6. **token 过期即全线停摆**：无人值守需人工介入，这是当前方案的天花板
