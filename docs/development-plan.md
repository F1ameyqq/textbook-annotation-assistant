# 模块化开发计划与两人分工

日期：2026-10-16。配套：[整体架构](architecture.md) · [接口约定](contracts-v1.md)。

目标：两人围绕相同数据合同独立推进，尽早跑通从输入到执行回执的纵向流程。正常题无需逐题人工批准，人工工作集中在异常、抽查与最终提交。

## 1. 建议分工

A = 用户，B = 技术搭档；这是按当前项目接触面的建议，可整块交换。

| 范围 | 主负责人 | 交付物 | 对方如何独立开发 |
|---|---|---|---|
| 来源接入与共享合同 | A | SourceBundle、类型校验、固定来源样例、规则版本 | B 离线使用来源样例 |
| 内容识别与模型适配 | B | EvidenceBundle、检测/OCR/公式后端、使用量事件 | A 使用固定证据/图谱样例 |
| 组题配答 | B | QuestionGraph、跨页/组合题/配答实现 | A 不等待真实算法即可生成执行计划 |
| 自动质量检查 | B 主写语义和覆盖检查；A 主写平台读回检查 | 同一 CheckReport 合同，两套独立入口 | 双方交叉审查误放行和漏题用例 |
| 平台交付与无头运行时 | A | 计划、浏览器会话、回执、未知保存核对 | B 使用模拟平台结果验证算法决策 |
| 异常工作台、任务恢复 | A | 异常列表、patch、状态与批次报告 | B 提供问题类型及证据，不写 UI |
| 预算与费用 | A 负责运行限额/账本；B 负责模型实际 usage 适配 | 每次调用记录和批次成本报告 | 通过统一调用事件联调 |
| 验收样本与业务政策 | A 管理合并；双方核准 | 来源可追溯的样例与规则 | 固定独立留出集，不随调参改答案 |

合同和共享规则由 A 负责最终合并；B 可以提出修改，不私自添加下游必须理解的新字段。重要合同变更需同批提供样例、迁移说明和双方消费者适配。

A 的平台端工作可能成为瓶颈，因此先用命令行/静态报告查看异常，复杂工作台后移；B 在 M1 同时提供叠框预览，减少 A 的前期界面工作。

## 2. 规划目录

以下为待创建目录；本轮只新增设计文档，没有创建应用骨架。

```text
src/annotation/
  contracts/           # 通用数据类型、版本及校验，唯一合同实现
  geometry/            # 原图、裁片和变换数学
  source/              # 本地导入、平台只读来源适配
  recognition/         # 分片、检测、OCR/公式及后端适配
  assembly/            # 语义、跨页、小问、题答关联
  quality/             # precheck / postcheck / coverage
  delivery/            # planner / usense adapter / reconciler
  exceptions/          # patch 应用、异常查询
  runtime/             # 调度、存储、模型网关、预算、浏览器生命周期
web/                   # 轻量本地工作台
config/policies/        # 版本化业务、平台映射、支持范围
tests/fixtures/        # 两人共用的真实及故障样例
evaluation/            # 留出集清单、指标与实验报告
data/runs/             # 本地运行产物，按 run/version 保存
data/browser-profiles/ # 本机登录配置，不入库
```

通用模型类型以 contracts 为唯一权威；如需 JSON Schema，由同一类型定义生成或校验，避免两套手工维护的规范。

算法模块不得依赖 delivery、浏览器或 web；quality 不执行写入；工作台通过应用接口提交 patch；runtime 编排模块但不写题型规则。

## 4. 按可验收成果推进

| 阶段 | A 的工作 | B 的工作 | 验收结果 |
|---|---|---|---|
| M0 合同与样例 | 汇总来源、固化类型与规则、准备模拟平台 | 把候选输出转换为合同，提供正常/异常样例 | 两台机器能读写相同产物；没有个人绝对路径；页/图/题身份不混淆 |
| M1 离线纵向闭环 | 固定图谱 → 计划 → 模拟执行回执；任务持久化、简单异常列表 | 单页普通题 → 识别 → 配答 → 覆盖/结构检查 | 正常样例无需人工点击进入模拟待提交；异常准确分流；中断可恢复，报告明确为模拟 |
| M2 实际平台闭环 | 独立无头登录与只读验证；探测草稿/OCR 时点；在明确允许范围完成单题写入、读回和接管 | 用真实算法替换固定图谱；做最小后置内容检查或 CONTENT_PENDING 分流 | 实际新增题符合计划；重启不重复建框；未知保存先核对；内容未验证不得算完整质量验收；最终提交人工负责 |
| M3 难例与异常修正 | 多片段执行、patch 后续跑、复杂内容后置检查 | 跨页、组合题、宽答案图、公式/图表、七选五 | 每类有真实验证样例与故障回归；未支持的题明确计入异常 |
| M4 小批评测与交付 | 批次进度、费用、人工耗时、部署和恢复说明 | 留出集评测、模型/规则路由、缓存与补救优化 | 输出自动完成率、漏错率、每百题人工分钟、每道合格题费用；据实确定自动放行范围 |

M1 的“模拟待提交”仅证明流程和合同能工作。M2 才验证平台实际效果。M3 不能只靠人工构造题证明真实难例支持。

第一轮采用单书串行写入。多书并行在单书恢复机制和平台多会话行为验证后再启用。

## 6. 每个模块的交付约定

每个任务交付：输入样例、输出样例、运行入口、已知限制、错误类型、相关验证结果，以及代码版本。提供最短复现说明，不依赖原聊天记录。

接口可以先用固定返回值接通，但模拟输出必须标注。一个模块尚未完成时，对方继续用已冻结样例开发。

共享分支使用普通 PR 整合；一人负责一个模块主改，另一人审查。各自的 GPT 读取同一版架构/合同，遇到合同变动先提交变更，不各自猜测补字段。每次联调以相同提交版本和相同样例为准。

阶段验收按证据进行：JSON 合法不是业务正确，模拟回执不是平台成功，检测框重合也不是题答匹配正确。

## 7. 当前最先推进的顺序

1. 双方完成 C01：冻结少量核心类型、固定样例和验收口径。
2. A 做 A01/A02/A04；B 做 B01/B02/B03，可并行。
3. A 加 A03，双方完成 I01。
4. 进入 M2 的真实单题闭环，再扩大题型和样书范围。

不先训练新检测模型、不先搭复杂工作台。先让一条正常路径自动走通，证明各模块能独立替换和恢复，再用实际失败样例决定主要投入。
