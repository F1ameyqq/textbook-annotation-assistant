# A 侧开发调度与验收

更新：2026-10-16（Asia/Shanghai）。本对话只负责 A 侧开发调度与验收，B 侧独立管理开发。技术语义以 [架构](architecture.md)、[合同](contracts-v1.md) 和 [开发计划](development-plan.md) 为准；提供给 B 的信息集中在 [B 侧协作交接](b-side-handoff.md)。

## 1. 谁做什么

| 角色 | 职责 |
|---|---|
| 用户 | 产品目标、业务口径、预算、线上允许操作范围及最终提交 |
| A 侧调度中心（本对话） | A 侧任务拆解、派发、复现验收和集成；维护接口提案、资料及跨侧联调问题 |
| A 侧开发（用户侧执行任务） | contracts、geometry、source、delivery、runtime、exceptions、quality 的 targetcheck/postcheck |
| B 侧开发（搭档及其 GPT） | 独立管理 recognition、assembly、quality 的 precheck/coverage；自行决定实现、人员、排期和内部验收 |
| A 侧复核者 | 对照 A 侧任务条款检查交付；可由独立子代理承担 |

A 侧调度中心可以分派本地子代理，但不向 B 侧派单、催排期或安排返工，不代替 B 做开发验收。双方交换接口版本、样例、变更说明及集成结果；A 侧核对 B 的交接产物是否符合共同约定并能被 A 消费，这不等于验收 B 的整个模块。发现问题时提供输入、版本、复现和影响，由 B 自主安排处理。

用户可以在本对话发“派下一批 A 侧任务”“验收 A 侧 <任务号/PR/提交>”“更新给 B 的资料”“核对交接接口”。调度中心每次先读取此文件与最新代码，再行动。用户于 2026-10-16 要求自动检查进度、验收和按路线派发后续任务；已配置绑定本对话的定期唤醒“1800 A侧开发调度与验收”（ID `1800-a`），当前 ACTIVE，每 15 分钟检查一次。自动化是实际触发器，本文件及 [调度状态](coordination-state.json) 保存路线与去重信息。

每次检查完成产物后再决定验收、返修和后续派单；执行 completed 不等于验收通过，验收通过不等于已集成。新阶段执行/验收分别新建对话；同一任务已有对话时在原对话补证据或修复，避免重复派发。既有 A 侧任务派发授权包含必要的定向跟进，不延伸到 B 或外部联系人。没有新进展时不重复通知；只有阶段结果、重要派发、失败或需要用户决定时简短汇报。

任务去重键为“任务号 + 阶段 + 基线版本”，保存对话 ID、产物版本、cursor 和下一依赖；创建前落盘意图、创建后落盘 ID，结果不明先查现有对话。以 C01 → A01/A02/A04 → A03 → I01 A 侧集成为当前开发主线，后续真实平台/难例阶段仍须具体任务单及有界范围。全部约定路线完成后停止扩张并暂停调度；未决业务政策、B 的接口确认或费用授权不假装已解决。运行需本机与桌面应用可用，见 [OpenAI Docs：定时任务](https://learn.chatgpt.com/docs/automations?surface=app)。

2026-10-16 用户进一步要求：“新的阶段性任务你新建对话做任务派发和验收”。从 A05 起，阶段执行和独立验收使用各自的新对话，本对话维护范围、依赖、结果与集成决定。先给执行对话具体任务单，再给验收对话独立标准；验收等待执行交付并释放线上会话，不能与执行者并行占用同一书籍/profile。任务对话创建成功仅表示已派发，不能记成开发完成。

## 3. A 侧派发与交付流程

1. 调度中心写任务单：可观察的目标、输入/合同版本、允许改动范围、依赖、验收条件、资源限额。
2. 执行者回执任务号、基线提交、工作分支及阻塞项。接单后记为 RUNNING。
3. 执行者提交代码、输入输出样例、复现命令、真实运行结果和未解决问题，转为 REVIEW。
4. 调度中心在对应提交上复现、检查失败路径；必要时安排独立复核。结论为 ACCEPTED、REWORK 或 BLOCKED。
5. 验收通过后安排集成；记录合并提交并运行受影响集成检查，通过后才记为 INTEGRATED、释放依赖。

状态：BACKLOG（等待依赖）、READY（可派）、RUNNING、REVIEW、REWORK、BLOCKED、ACCEPTED、INTEGRATED。BLOCKED 必须写清缺少什么以及恢复条件。代码写完、测试自报通过、已合并是三种不同事实。

若单独验收某任务时使用固定上游样例，记录该样例版本；真实上游接入后仍需联调。依赖已经 ACCEPTED 但尚未集成时，可显式指定其提交供下游开发；不能按分支名猜测内容。

A 负责维护共享合同实现、geometry 公共接口、根依赖文件、公共样例和 A 侧集成入口，避免多个 A 侧执行者同时修改。跨侧合同的必填字段或语义变更须形成提案，说明版本、样例、迁移及消费者影响，经双方确认后采用；A 内部验收不代表 B 已接受接口。两侧分别拥有 quality 的不同入口，共享文件变更提前协调。

## 5. A 侧验收与跨侧联调的区别

每张 A 侧任务单在开始前写清适用的验收层级，交付时逐项标记“通过/失败/未执行及原因”。下列算法质量信息用于跨侧联调所需的证据沟通，B 的内部研发验收由 B 自行组织。

| 层级 | 必需证据 |
|---|---|
| 合同与模块 | 确切提交、运行环境、固定输入输出、类型与引用检查、关键失败样例 |
| 算法质量 | 可追溯原图、叠框/配答结果、独立留出样本、漏题与错配统计；声明调参与评测是否共享样例 |
| 执行与恢复 | 动作计划、intent/receipt、模拟或实际类型、超时后读回、重复动作检查 |
| 真实平台 | 明确书籍/题目/范围、实际效果证据、刷新读回、原有数据未受意外影响；由具备本机访问权限的一侧执行 |
| 成本 | 运行范围、实际调用/失败/重试用量、价格版本、缓存、合格题数；不调用付费模型时标记“未测” |

调度中心复现关键路径，不仅阅读开发者的“已完成”。独立复核优先检查作者容易遗漏的失败条件；多个代理同意不等于业务正确。若本机无法复现，保留为未验收并给出缺失环境/证据；不能以一段成功日志代替真实平台效果。

上述 ACCEPTED/REWORK 等状态只管理 A 侧任务。B 侧交接只记录“产物版本、兼容性检查结果、A 的集成就绪情况、待沟通问题”，不标记 B 开发完成、返工或排期。模型实现与内部测试方法由 B 自主选择，双方共同约定跨侧输出及质量边界。

线上操作采用本文件“当前测试用书与授权”中的 `46007447` 范围。开发派单不自行扩大范围，最终提交仍由人工负责。付费模型任务先给出预算上限、数据范围与停止条件；离线模块任务不需要等待这类确认。
