## 二、我们实际用的OCR模型

|用途|实际后端与版本|模型／权重|运行方式|
|---|---|---|---|
|普通中英文文字、题号、行内文字及局部回补|`rapidocr-onnxruntime==1.4.4`|检测 `ch_PP-OCRv4_det_infer.onnx`；识别 `ch_PP-OCRv4_rec_infer.onnx`；方向分类 `ch_ppocr_mobile_v2.0_cls_infer.onnx`|本地CPU；当前普通Python环境ONNX Runtime 1.25.1|
|独立公式图块转LaTeX候选|`rapid-latex-ocr==0.0.9`，RapidLaTeXOCR|`image_resizer.onnx`、`encoder.onnx`、`decoder.onnx`、`tokenizer.json`|独立本地公式环境，CPUExecutionProvider；该环境ONNX Runtime 1.31.0|
|分栏、行投影、连通域、候选区域|既有OpenCV／几何规则|不是另一个语义OCR模型|本地几何处理，再结合来源、组装和质量检查|
|最近的Q16／阅读材料／剩余14行内容补录|固定原图上的模型目视观察、既有OCR及显式转写草稿|不属于重新运行上述OCR，不是人工金标准|最近两批没有新增OCR、公式推理或付费调用|

因此，准确的简述是：**文字OCR用RapidOCR封装的PP-OCRv4检测／识别，方向分类仍是v2；公式用独立RapidLaTeXOCR。** 不是统一“PP-OCRv4三件套”，也不是DeepSeek承担当前OCR。

本轮直接核实了普通环境安装版本、配置和三份ONNX文件，摘要与历史真实OCR回执一致。普通Python环境没有安装rapid-latex-ocr；它位于已有独立公式环境，本轮也核实其版本和四份本地文件摘要，全部与固定锁文件一致。仅检查依赖和权重，没有为本报告重跑识别、安装软件或下载权重。

可追溯证据：`evaluation/book-46007447-recovery.json`、`tests/fixtures/book46007447/ocr-evidence.json`、`evaluation/book-46007447-formula-batch.json`、`evaluation/formula-cpu-runtime-lock.json`。本轮安装与文件核查见 [核查记录](../evaluation/book-46007447-project-alignment-20261020.json)。

公式后端的输出仍可能漏符号、错幂次或多次同错，不能用置信度、代数成立或多模型一致替代原像素核对。OCR文字框也不天然等于整题边界；整题组装、共享材料、选项拆分、跨页续接和配答是额外工作。

## 五、下一步如何分工，避免继续互相等待

1. **B负责内容交付本身。** 继续完成Q16和阅读材料18项逐项核对、差异修订与新检查；新8份答案证据等待真实题页身份时仍保留可核内容和出处，不能凭题号猜配；Q9现有答案和跨页证据继续整理，真实题页未确认时明确留缺口。
2. **来源材料按差量补齐，不以“对方做完OCR”为前提。** 当前明确缺的是章节目录/起止依据、Q9反思题页和这8份答案的对应题页；已在本机的Q16、阅读题页不重复索要。哪一侧能合法只读取得原图，哪一侧就交原图、SHA、尺寸、阅读顺序及页码观察，不要求先标注或识别完成。
3. **A负责真实消费者和执行边界。** 先确认复杂公式、图形、共享材料/三任务、多页来源、答案证据暂存所需字段及政策范围，再对一个固定候选包实际消费、生成计划、模拟和独立读回。不能把Q1/Q4限定政策自动迁移到Q9/Q16或整章。
4. **共同固定交付对象，而不是互报“做完”。** 每次交接仅约定一个提交、一个包摘要、实际案例范围及具体预期；接收方记录真实验证及差异。B的18项内容问题、A消费者适配和整章来源分母分别追踪，不能由机器结构检查互相代签。
5. **演示工具另设产品决策。** 若恢复人工预框，先补齐存储/画布脚本/样式，再验0.5×/2×坐标回投、独立图片身份、保存失败、导出重导入和多页历史，最后才谈自动整题候选。当前仅调查，不改变此前暂停约定；不新增模型收费或网站写操作。
