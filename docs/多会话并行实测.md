- 实测脚本：`tools/parallel_probe.py`（本次新建，可重复运行）

## 0. 一句话结论

1. **多本书并行：不可行。** 该账号当前可见书籍 `total = 1`，只有 `46007447`（名校课堂八年级数学上册，214 页 / 94 题，状态"标注中"）。所以"并行"只可能发生在**同一本书内部**。
2. **同一 token 双会话并行：可行。** 两个独立持久化 profile 同时登录同一账号、同时选同一本书、各自翻页/加载题目，**互不影响**，token 在约 5 分钟的连续双活期间没有被踢、没有报错、没有限流。
3. **并发写入：不安全（未实测，属推断）。** 平台没有任何"占用/心跳/互斥"迹象，两个会话的状态完全独立；因此两个会话**同时对同一题**画框并提交，风险是"最后一次覆盖 + 另一侧看不到已保存结果"。建议按题号分区，提交串行。

## 5. Q3：并发下的写入安全性

### 5.1 实测到的（证据）

1. **本次运行没有产生任何写请求**：两会话各 30 次 `/qieti/api/` 请求，`non_get_requests` 均为 `[]`。所以"不加防护的并行会不会顺手改数据"在本探针里不成立——探针本身就是干净的。
2. **两个会话的状态完全独立**：页码框、counts、当前题目、画布指纹，在一侧操作后另一侧全部不变（§4.2/§4.3）。唯一共享的是**同一本书、同一条 token、同一份服务端标注数据**。
3. **并发读同一题结果一致**（§4.4）。
4. **没有任何"他人正在编辑/占用"的提示**：`dialogs=0`，且两个会话都成功"选择书籍"同一本、都正常进入编辑态。

### 5.2 推断的（标注清楚）

- **写冲突形态大概率是"后写覆盖 + 另一侧不刷新"**：平台既有的标注读取接口（本仓 `bin/live_draw_test2.py` 里实测用过的路径）是 `.../get_manual_annotations_unified_by_order_in_level/{book}/{order}` 这种"题号在路径里"的形态，说明服务端以 (书, 题) 为键组织标注数据；两会话各自持有一份前端标注数组，提交时对该题整体或增量 POST。两个会话同时对**同一题**提交 → 后提交者的数据覆盖先提交者，且先提交者页面上不会出现对方的框（它不会自动拉取）。
- **平台未见写锁/租约机制**：`claim_book` 字面像"领取"，但实测同一账号两个会话可同时进入同一本书，未见任何"已被占用/释放"提示，也未见到心跳或 presence 类请求。因此**不能指望平台替我们做互斥**。
- **"状态：标注中"是业务状态**，不是并发锁（推断：它是人工流程状态，与本次双会话共存无冲突）。

### 5.3 关于"想验证但没做"

按任务约束，**没有真的提交**，所以"两会话同时提交到底谁赢、会不会产生重复框/孤儿框"**没有实测数据**。要补这个证据，需要一个可丢弃的题（例如平台上的练习书/测试书）由人工授权后做一次双提交对照实验；本账号只有一本正式书，不适合。

## 6. 风险清单

| 风险 | 实测/推断 | 现状与应对 |
|---|---|---|
| **token 并发** | 实测：约 5 分钟双活无异常；**长时未测** | 只要平台不加"单会话校验"，双会话稳定。上线前把"健康检查"写进流程：每轮先 GET 一次 books（200 且 `code=0`），失败即停，不要反复重登（登录需人工） |
| **平台限流** | 实测：0 次 429/5xx（60 次 GET/~5 分钟） | 密度很低，未触边界。若把并行数提到 4+、或频繁轮询 counts，需重新测 |
| **指针滞后是否跨会话** | **实测不跨** | 会话内滞后仍在（SOP 最大坑），但并行天然绕开：每个会话只操作自己的窗口 |
| **profile 目录锁** | 实测：必须两份目录 | 每并行 1 路 = 复制一份 117M profile；N 路 = N×117M 磁盘 |
| **内存/CPU** | 实测：2 个 Edge 实例（headless）本机正常 | 每实例约 0.3–0.6GB；本机 4 路以内应可行（未实测） |
| **两端缓存不一致** | 推断 | 会话 A 提交后，会话 B 不刷新就看不到 A 的框；任何"另一侧已改"的判断都必须走"重新加载题目 + 比对 counts" |
| **一本书只有一个领取人** | 未验证 | 若能拿到第二个账号，需复测"两个不同账号同时开同一本书"——那才是真正的业务并发风险 |

## 7. 建议

### 7.1 推荐形态：**测量并行、录入串行**

```
阶段1（并行，只读/只算）:  A 会话负责题号 [1..47]，B 会话负责 [48..94]
   每会话循环：goto_page → 双击加载题目 → 等 counts 稳定 → 页内测量 → 写 data/derived/... 文件
   两侧写不同文件，零共享写面
阶段2（串行，单会话）:     统一录入/提交，按题号顺序一题一题来
```

理由：本实验证明并行的**收益**在"翻页 + 加载 + 测量"（每路 4.7–5.0s 翻页、1.9–2.6s 加载，两会话不排队 ≈2× 吞吐），而风险全部集中在"同时写同一题"。把写入收回到单会话，风险归零，收益保留。

### 7.2 如果一定要两会话都可写

硬性约束三条：
1. **题号区间严格不相交**，任何时刻不允许两个会话加载同一题（本次实测证明"能同时加载"≠"能同时写"）。
2. 每个会话提交前做一次"重载校验"：重新双击加载该题 → counts 与内存中的框数量比对 → 不一致就放弃并记录，不覆盖。
3. 提交串行化（文件锁 / 单 worker），一次只允许一个会话在提交。

### 7.3 不要做的事

- 不要用同一个 profile 目录开两个会话（Chromium 单实例锁 → 第二个直接起不来）。
- 不要在两会话间共享"当前题号/当前页"这类隐式状态——它们是**每会话独立**的（实测），共享只会制造 bug。
- 不要把 `Live.goto_page()` 返回的 `changed` 当成"翻页成功"的唯一判据（见 §8，它会漏判）。

## 8. 方法论陷阱（本次踩到并修正，建议写进 SOP）

1. **画布指纹不能用作主判据。** v1 用 `canvas` 左上 40×40 块做 hash，实测会出现：读到全 0（异步重绘中/画布被清空）、同一页两次读数不同（pdf.js 重绘时序）。改成"整幅网格采样 + 连续两次相同才算稳定"，并把**页码框 `value`** 提升为权威判据。
2. **`counts` 非全零 ≠ 题目加载完成。** 上一题已加载时 counts 本来就非零，用 `sum(counts)>0` 判完成会把 no-op 当成功（v2 里 A 已加载 q64 后再次 dblclick 同一节点，0.05s 就"完成"，实际什么都没发生）。正确判据：**`当前题目` 等于目标题号，且 counts 连续两次读相同**。
3. **这两个 bug 会伪造出"跨会话污染"。** v3 一轮里出现：B 加载 q12 的瞬间，读到 A 的 counts 从全 0 变成 `{1,1,1}`，看起来像"B 影响了 A"。真相是 **A 自己的 q30 异步加载晚到**（q30 的 counts 恰好也是 `{1,1,1}`），因为 A 的加载判据提前返回了。修好判据后重跑，同一段变成干净的 `a_affected:false`。
   → **教训：任何"并行隔离"实验，必须证明两侧都已进入稳定态再比较，否则读到的只是自己的异步尾巴。**
4. 终端中文乱码是 cp936 显示问题，判断数据请直接读 JSON（UTF-8）。
