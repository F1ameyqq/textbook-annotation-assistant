## 0. 一句话结论

**纯 OCR + 固定规则在本书上"部分够用、但对数学内容不够用"。**

- 够用的部分：在**已知框坐标 + 正确页映射**的前提下，字段级抓取是可行的——题干文本 14/14 全部取到，5 个选择题的选项 5/5 逐字正确，答案字母大部分干净（如第1题`B`、第2题`D`、第7题`D`）。
- 不够用的部分：① 数学公式不可机器解析（分式、上下标、根式大量丢失，`−`→`一`、`+`→`十` 系统性错误）；② **置信度无法发现"框选错区域"这类静默错误**（错区域也能给出 0.957~0.9999 的置信度）；③ 整页 OCR 输出 126 行碎片，没有任何"题号归属"，纯规则无法把行拼成题；④ 含图的题（第5、6、12题）必须靠视觉模型。
- 附带重大发现（见 §4）：任务给的前提"页 8/9/10 的框坐标可直接用"**只对了一半**——坐标是对的，但**文件名整体错位一页**（`page_index N` 应对应 `46006966_page_{N-1}.jpg`）。按字面用 `page_N.jpg` 会得到"高置信度但语义完全错误"的结果。

## 2. 后端与 GPU：诚实结论

任务要求优先用 GPU（RTX 5060 8GB，sm_120）。**逐条真实尝试后的结论是：本机无法把 GPU 用到 OCR 上，本次全部走 CPU。**

| 尝试路径 | 结果 | 证据 |
|---|---|---|
| `paddleocr 3.7.0 + paddlepaddle 3.3.1` GPU | **不可用（未运行）** | `paddle.device.is_compiled_with_cuda() == False`，`paddle.device.cuda.device_count() == 0` → 本机 paddlepaddle 是 **CPU 轮子**，GPU 路径在编译期就不存在；且 PaddleOCR 3.x 首次运行需联网拉模型 |
| `rapidocr_onnxruntime(use_cuda=True)` → CUDA ExecutionProvider | **静默回退 CPU** | `onnxruntime 1.25.1` 的 `get_available_providers() == ['AzureExecutionProvider','CPUExecutionProvider']`，无 `CUDAExecutionProvider`。构造**不报错**，但实测 session providers 仍是 `['CPUExecutionProvider']`。源码依据：`rapidocr_onnxruntime/utils/infer_engine.py::_check_cuda()`（L95–129）在 CUDA EP 不在 available_providers 时返回 False，`_get_ep_list()` 只放 CPU EP |
| `torch 2.11.0+cu128` 直连 GPU | **可用**（但**不能用于 OCR**） | `torch.cuda.is_available() == True`，设备 `NVIDIA GeForce RTX 5060 Laptop GPU`，compute capability `(12, 0)`；512×512 CUDA 矩阵乘成功。**但本机没有任何可离线加载的 torch OCR/版面模型**，所以这份算力落不到 OCR 上 |
| 装 `onnxruntime-gpu` / `pix2text` / `rapidocr_paddle` | **失败（网络不可达）** | `pip download --no-deps onnxruntime-gpu==1.25.1` 180 s 未返回被终止；`pip download --no-deps --timeout 8 --retries 1 six` 90 s 未返回被终止；TCP 探针 `pypi.org:443` / `files.pythonhosted.org:443` 见 JSON `backend.probes.network` |

补充事实（会影响其它成员的判断）：`import paddle` 之后再 `import torch`，在本机**偶发** `OSError: [WinError 127] 找不到指定的程序 ... torch\lib\shm.dll`（本次在先行导入 torch 的进程里复现为正常）。脚本已把两种 import 顺序写进 `data/derived/analysis/route_c_probe_tmp/*.py` 子进程取证。另外 `nvidia-smi` 在本沙箱内挂起不返回（已放弃，改用 torch 查询）。

> **报告口径**：`meta.gpu_used_for_ocr = false`。任何"路线C 用了 GPU"的说法都是不成立的。

## 6. 固定规则配答（配对键 = `order_in_level`）

规则：以 `order_in_level` 为键，把 `question` / `choice` / `answer` / `analysis` 归并成题。36 条标注全部可解析出整数 `order_in_level`（`unparsable_order_rect_ids = []`），得到 **14 题**。

| 字段 | `type` 字段口径 | 说明 |
|---|---|---|
| 题干 | **14 / 14** | 每个 order 至少 1 个 `question` rect；shift1 下 16 个题干框全部有文本 |
| 选项 | **5 / 14** | 不是缺口：这 14 题里本来只有 5 题是选择题（order 1,2,7,8,14），且 **5/5 选项逐字正确** |
| 答案 | **14 / 14** | 每个 order 都有 `answer` rect；但内容质量分化，见下表 |
| 解析 | **1 / 14** | `type='analysis'` 只有 order 10 一个 |
| 题干+答案+解析齐全 | **1 / 14** | 仅 order 10 |

### 6.1 用"规则"而非 `type` 字段重新判定的完整率

`type` 字段**不可靠**：`answer` 框里混着"单字母答案"和"整段解析"。按内容判据（答案框 OCR 文本 ≥30 字且含 `（1）`/`解析`/`∵`/`=`）重新统计 shift1 结果：

| 类别 | 数量 | order |
|---|---|---|
| 短答案（字母/符号）可用 | 7 | 1(`B`), 2(`D`), 3(`④`), 7(`D`), 8(`A`), 10(`6`), 14(`D`) |
| 长文本解析（实为答案解析） | 4 | 6, 11, 12, 13 |
| 噪声 / 不可用 | 2 | 5(`x（24 2x 40`), 9(`po`，置信度 0.506) |
| 完全无文本 | 1 | 4（`status=no_text_detected`） |

→ **答案可得 11/14；解析可得 5/14**（order 6, 10, 11, 12, 13）。也就是说：**按 `type` 字段算，解析只有 1/14；按内容算，解析其实有 5/14**。字段级元数据与内容不一致，纯规则必须靠"内容启发式"兜底。

### 6.2 配对键本身的局限（真实样例）

- `order_in_level` 是**标注会话内的全局序号**，不是课本印刷题号：order 14 对应的是课本第 6 页的印刷第 **1** 题（`如果关于x的方程（x一9）²=m十3…`）。所以 `order_in_level` 只能做**内部配对键**，不能当"第 N 题"直接对外使用。
- order 5 和 order 6 的题干**各被拆进 2 个 rect**（`question_split_across_rects=[5,6]`），简单按 rect 拼接会把图形碎片（`5`/`m`/`3m`）混进题干。

### 7.4 其它已发现的问题

1. **框左边界切掉题号**：`p9/question/ord8` 的 `x1 = 56.0`，而裁切图左缘可见被切掉一半的印刷题号 `8`（见 §7.1 右图）→ 题号被裁掉，行首数字检测失败。16 个题干框里 8 个拿不到行首数字，主要就是这个原因。**"行首题号"不能当稳健的配对键。**

## 8. 必须靠 VLM（或专用公式模型）才能补的能力

按"纯 OCR + 规则为什么做不到"排序：

1. **数学公式 → 结构化表示（LaTeX/MathML）**。分式、根式、上下标、指数、绝对值在 OCR 阶段已被压平或丢失（§5.1、§7.3）。这不是后处理能补的，必须在**识别阶段**换成公式识别模型或 VLM。→ **必须 VLM / 公式模型**。
2. **图形与几何关系**。第 5、6、12 题含示意图，OCR 只能给出散落的尺寸标注（`5m`、`3m`、`xm`），得不到"围栏靠墙""梯子滑动""取整函数图象"这类语义。→ **必须 VLM**。
3. **行 → 题的结构化归属**。整页 OCR 输出 126 行碎片，行序还会错乱（选项 C/D 排在 A/B 前），且 `order_in_level` 不是印刷题号。把行拼成"题干 + 选项 + 小问"需要版面/语义理解。→ 规则可做粗拼（靠框坐标），**鲁棒版需 VLM 或版面模型**。
4. **静默错位的自检**。identity 映射下 OCR 给出 0.957~0.9999 的高置信度错误文本；置信度对此**零警示**。要自动发现"这段文本答不上这道题"，需要语义校验（VLM 或跨源一致性检查）。→ **VLM 最直接**（非 VLM 办法见下）。
5. **`type` 字段与内容不一致的判定**。`answer` 里既有 `B` 也有整段解析；`analysis` 只有 1 条但真实解析至少 5 条。判定"这是答案还是解析"是语义任务。→ 规则+长度启发式可部分替代，**准确判定需 VLM**。
6. **数学符号的上下文纠错**。`一`→`−`、`十`→`+`、`㎡`→`m`、`x。`→`x₀`、`la|`→`|a|` 这类错误有强上下文规律，纯字符串替换会误伤中文正文（"一"本来是汉字）。→ **需模型**。

**不需要 VLM 就能补的**（避免把工作量估高）：
- 页号 off-by-one（§4）：靠平台元数据或一次浏览器会话确认即可，**不需要 VLM**；用我加的"选项 A./B. 判据 + 行首题号判据 + 答案与题干一致性"就能自动发现。
- 233/234 宽图的多页拼版切分：几何沟检测已够用（`verify_report.md` §2 已做）。
